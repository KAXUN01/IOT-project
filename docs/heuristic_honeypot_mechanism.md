# Heuristic-Driven Honeypot Mechanism for IoT Network Defense

## 1. Executive Summary
This document outlines the architecture, mechanism, and implementation strategies for the "Heuristic Analyst and Honeypot Management" module of the IoT security research project. The core innovation of this system lies in the **Integrated Heuristic-Deception Feedback Loop**, which combines lightweight anomaly detection with active deception (honeypots) to create a highly adaptive, automated defense system.

## 2. Integrated Heuristic-Deception Feedback Loop
Traditional security systems often rely on either static honeypots (which might not be discovered by attackers) or standalone anomaly detection (which is prone to false positives). 

This research integrates both into a synergistic loop:
1. **The Tripwire (Heuristics):** The heuristic analysis engine continuously monitors network traffic. When it detects an anomaly (like a DoS attempt or scanning), it acts as a "tripwire" without immediately dropping the traffic.
2. **Active Deception (Redirection):** Instead of immediately blocking the suspicious traffic (which could disrupt legitimate traffic in the event of a false positive), the system redirects it to a highly instrumented, isolated honeypot environment.
3. **Intelligence Gathering (Honeypot):** The attacker is engaged within the honeypot, believing they have compromised a real, vulnerable IoT device. The honeypot captures high-fidelity, actionable intelligence (e.g., origin IPs, specific commands executed, malware dropped).
4. **Permanent Mitigation (Policy Engine):** The extracted intelligence is confirmed as malicious (since no legitimate user interacts with the honeypot). It is then fed back to the Policy Engine to create robust, high-confidence network blocking rules across the infrastructure.

## 3. Core Component Deep-Dive

### 3.1. Heuristic Analyst (Anomaly Detection)
The Heuristic Analyst is responsible for continuous, lightweight monitoring of the network state.

*   **Mechanism:** It interfaces with the SDN switch infrastructure via the **Ryu SDN Controller**. It periodically polls flow statistics (packet counts, byte counts, flow duration) from the switches using OpenFlow protocol messages.
*   **Baseline Profiling:** Over time, the system establishes a "normal" baseline traffic profile for the IoT network (e.g., typical bandwidth usage, expected connection frequencies, standard communication protocols for normal IoT device operation).
*   **Detection Strategy:** The real-time metrics are continuously compared against this baseline. Significant deviations flag an anomaly. 
    *   *DoS Attacks:* Characterized by a massive spike in flow rates or packet volume directed at specific endpoints.
    *   *Network Scans:* Characterized by a single host rapidly connecting to multiple ports or multiple subsequent IP addresses in a short time window.
*   **Alert Generation:** Upon detecting an anomaly, the Heuristic Analyst generates an alert and forwards it to the Policy Engine for traffic redirection.

### 3.2. Honeypot Management
This component manages the deception environment to safely contain and analyze threats.

*   **Containerized Environment:** Honeypots are deployed using **Docker**. This allows for the lightweight, rapid, and reproducible deployment of environments that emulate vulnerable IoT devices (e.g., IP cameras with default weak credentials, vulnerable smart home bridges).
*   **Dynamic Emulation:** Emulating IoT services efficiently requires minimal resources. Docker containers can securely isolate the attacker from the host system while providing realistic simulated services (like SSH, Telnet, or HTTP web interfaces common on IoT devices).

### 3.3. Threat Intelligence Extraction (Log Parsing)
Raw honeypot logs are not actionable on their own and require automated processing.

*   **Scripting:** Automated scripts monitor the honeypot logs (e.g., Docker container logs, Syslog, or structured JSON logs generated by specific honeypot software like Cowrie).
*   **Extraction:** The scripts parse these logs to extract definitive Indicators of Compromise (IoCs):
    *   **Attacker IPs:** The exact source IP address making the malicious connection.
    *   **Commands Executed:** The bash/shell scripts the attacker tried to run post-compromise.
    *   **Dropped Payloads:** URLs or hashes of malware the attacker attempted to download into the IoT environment.
*   **Feedback Delivery:** This precise, confirmed threat intelligence is formatted and sent to the Policy Engine for final action.

## 4. Implementation Guide & Development Roadmap

### Phase 1: SDN Network Intelligence (Ryu & Heuristics)
1.  **Ryu Flow Polling:**
    *   Write a Ryu application that sends `OFPFlowStatsRequest` messages to connected OpenFlow switches at a set interval (e.g., every 5-10 seconds).
    *   Implement an event handler for `OFPFlowStatsReply` to parse and store the incoming flow statistics (src IP, dst IP, packet count, byte count).
2.  **Baseline & Heuristic Logic:**
    *   Implement an algorithm (e.g., Moving Average, Exponential Smoothing, or a statistical thresholding mechanism) to establish the traffic baseline.
    *   Translate the "deviation" logic into Python conditions. For example, if `current_packet_rate > (baseline_rate * 1.5)`, trigger a scan/DoS alert.

### Phase 2: Docker Honeypot Infrastructure
1.  **Image Selection/Creation:**
    *   Use existing lightweight honeypots like *Cowrie* (for SSH/Telnet brute force logging, very common in IoT botnets like Mirai) or *Dionaea* (for malware capture).
    *   Customize the Dockerfiles to emulate the specific file systems, device banners, or web interfaces of vulnerable IoT devices targeted in your research.
2.  **Docker Management:**
    *   Ensure the honeypots are running on an isolated virtual network that cannot route back into the real production IoT network, protecting the real devices from lateral movement.

### Phase 3: The Redirection Policy Engine
1.  **Alert Handling:** The Policy engine must have a mechanism to receive the "Tripwire Alert" from the Heuristic Analyst (e.g., internal function call if in the same script, or a message queue like RabbitMQ/ZeroMQ).
2.  **Flow Modification (Redirection):** When an alert is received regarding a suspicious Source IP (Attacker) and Destination IP (Victim IoT Device), the controller instructs the OpenFlow switches to modify the traffic flow:
    *   Change the destination MAC and IP address from the real victim device to the IP/MAC of the Honeypot container.
    *   Output the flow to the physical or virtual switch port connected to the honeypot infrastructure.

### Phase 4: Threat Parsing and Permanent Mitigation
1.  **Log Parsing Script:**
    *   Write a Python script using libraries like `json` or `re` (regex) to continuously tail and monitor the honeypot logs in real-time.
    *   Filter the logs to extract the Source IP of any connections that proceed beyond a certain threshold (e.g., an attempted shell command execution).
2.  **Mitigation Loop:**
    *   The parsing script sends this confirmed malicious IP back to the Policy Engine.
    *   The Policy Engine issues an `OFPFlowMod` command to the border switches with an action to `DROP` all traffic originating from that confirmed malicious IP, permanently mitigating the threat with high confidence.
